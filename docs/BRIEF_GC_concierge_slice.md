## Критическое ограничение (гардрейл)
ИИ **может** менять: порядок, акцент, объяснение, формулировку, формат.
ИИ **не может** менять/выдумывать: факт наличия, цену, условия поставщика, ограничения, факт подтверждения. Наличие и цена берутся ТОЛЬКО из ответа поставщика. Нет ответа → нет Quote.

## Поток (первый срез)
```
Гость: "Хочу завтра вечером на яхту, 4 человека, закат"
  → BookingIntent {категория, дата/время, кол-во, бюджет, заметка}   (GC-03)
  → Matching: выбрать поставщиков категории из каталога              (GC-02)
  → AvailabilityRequest: n8n шлёт request-to-book в Telegram          (GC-04)
  → Поставщик отвечает: "18:30 / 16 000 ₽" (или отказ)
  → Нормализация в Quote {slot, price, supplier}                     (GC-05)
  → Гость видит подтверждённый вариант, подтверждает
  → FSM заявки: NEW→SENT→QUOTED→CONFIRMED→CLOSED, запись в concierge_orders (GC-06)
```

## Критерии приёмки
1. Каталог `concierge_suppliers` из ≥2 поставщиков читается Matching-нодой.
2. Заявка (первый тест — через ручной ввод оператора, действие `concierge_intake_create` в WF10) создаёт запись в `concierge_orders` со статусом NEW и рассылает request-to-book в Telegram минимум одному поставщику.
3. Ответ поставщика (принять+цена) переводит заявку в QUOTED и пишет строку в `concierge_quotes` с этой ценой (не выдуманной).
4. Подтверждение → CONFIRMED в `concierge_orders`. Таблица `bookings` не тронута (проверить, что не менялась).
5. Изменения реально применены в runtime (проверено триггером). Регресс: процессы 01/02/03/09/10 всё ещё active, их вебхуки живы.
6. Бот-канал (WF20) собран и ждёт только вставки учётных данных `telegramApi` пользователем — без токена в коде.
